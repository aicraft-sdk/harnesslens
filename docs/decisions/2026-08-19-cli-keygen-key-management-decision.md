# CLI local key management (`harnesslens keygen`, Phase 4)

## What Changed

Phase 4 of `docs/plans/2026-08-19-evidence-package-plan.md` added the CLI's first-ever
key-management capability: `harnesslens keygen [--force]`. `src/keys.ts` generates an Ed25519
keypair with `node:crypto` and writes the private key to `~/.harnesslens/signing-key.json`
(mode `0600`, parent directory `0700`, created if missing). It never overwrites an existing key
file unless `--force` is passed, uses an exclusive (`wx`) file-create flag to close the
TOCTOU race window between an existence pre-check and the write, and re-`chmod`s both the
directory and file after write since `mkdirSync`/`writeFileSync`'s `mode` option is only honored
on creation. The command prints the base64 public key and a copy-pasteable `curl` command for
registering it against the live backend's `POST /accounts/:accountId/signing-keys`; it never
prints or transmits the private key, and never calls that endpoint itself. `loadSigningKey()`
(consumed by a later phase) never surfaces a raw filesystem error — only messages pointing back
at `harnesslens keygen`.

## Why

This is the CLI's first capability that persists secret material to disk, so the file-handling
discipline needed to be established correctly on first use rather than retrofitted later: a
leaked or corrupted private key is unrecoverable for whatever account it was registered under.
Making key registration a printed suggestion rather than an automated `POST` keeps the CLI's
existing zero-network-by-default posture intact for `keygen` itself (see ARCHITECTURE.md
"Determinism/safety guarantees") — the command's only side effect is a local file write, and the
CLI does not need to manage `accountId`/`apiKey` inputs to generate a key.

## Alternatives Considered

- **Auto-register the key via `POST /accounts/:accountId/signing-keys` during `keygen`:**
  rejected — would require `keygen` to also accept and manage `accountId`/`apiKey` inputs,
  expanding its scope and turning a purely local command into a network one; printing a
  copy-pasteable command keeps registration an explicit, separate step the user controls.
  Follow-on: `docs/plans/2026-08-19-evidence-package-plan.md` (design rationale item 10).
- **OS keychain/credential-manager integration instead of a plain file:** not pursued for this
  phase — the plan's stated dependency constraint keeps the CLI's `dependencies` empty
  (`node:crypto`/`fs`/`os`/`path` only); a cross-platform keychain integration would need a new
  dependency or platform-specific shell-outs, which is new, unaudited attack surface for a first
  implementation. `0600`/`0700` file permissions plus `--force`-gated overwrite were judged
  sufficient for this phase.
- **Silently overwrite an existing key on every `keygen` run:** rejected — an existing key may
  already be registered against a live account; silently replacing it without `--force` would
  make an already-registered public key unrecoverable without warning.

## Impact

- **Who is affected:** CLI users adopting the signed/verified submission flow (later phases —
  `submit --sign`, `verify-package`); no existing command's behavior changed.
- **Migration:** none — this is a new, opt-in subcommand; the scorer/`multi`/`--badge` paths are
  unmodified.
- **Ongoing maintenance:** the `~/.harnesslens/signing-key.json` file contract
  (`algorithm`/`privateKeyPkcs8Base64`/`publicKeyBase64`/`createdAt`) is now load-bearing for
  `loadSigningKey()` and any future phase that signs a submission; changing its shape requires a
  compatible migration path for keys already generated by this version.
